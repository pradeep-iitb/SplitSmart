1. PS Overview

SplitSmart turns a receipt photo into a fair, itemized group split. The key challenge is not ML research — it is reliable web engineering, clean UX, robust parsing, correct financial logic, and smooth client-side execution.

Input

A receipt image or a manually entered expense, plus a group of members.

Core transformation

Image → OCR → structured items → user correction → item assignment → fair split.

Output

Exact per-member balances and simplified “who pays whom” settlements.

3. Architecture We Will Use

No backend is required. Logic runs inside the user's browser. Heavy OCR/ML runs in Web Workers; financial logic runs as normal TypeScript functions; state persists locally.

UI Layer — React pages/components, mobile-first interaction, error/loading states
Application State — group, expense, receipt-draft and settlement state
Business Logic — parsing, split engine, tax distribution, rounding, balance calculations, debt simplification
Workers — Tesseract.js OCR and MobileBERT categorization off the main thread
Persistence — IndexedDB/localStorage for groups, expenses, settlements and cached state

4. Most Important: Shared Integration Contract

Everyone can work independently only if we agree on the same data shapes, ownership boundaries and engineering rules first. These are the shared technical decisions that should not change casually.

Money representation
Always store money as integer paise.
Never use floating-point rupee values in core calculations.
IDs
Every group, member, expense, item and settlement gets a stable unique ID.
Core data types
Keep all shared interfaces in one types/ folder. No duplicate local versions of the same type.
UI vs logic
React components call pure functions. Calculation logic must not live inside page components.
OCR output contract
OCR module returns raw text, line/word confidence and enough metadata for the review screen to highlight uncertain content.
Parser output contract
Parser returns a structured ParsedReceipt object; it does not directly update UI or persistence.
Split engine input
Consumes structured item/member/payment data only. It should not know about React or OCR.
Workers
OCR and ML inference run in Web Workers to avoid freezing the UI.
Persistence
Only the state/persistence layer writes to IndexedDB. Other modules use exposed functions.
Error strategy
Every module returns recoverable errors. Bad OCR must never leave the app stuck; manual correction must remain available.

5. How It Is Expected to Work in Actual Judging

Judges will test the full flow on phone and desktop, and the whole interaction should feel fast and recoverable. They will care more about a smooth experience than perfect OCR.

1
Clear restaurant bill
Items, GST/tax and total should parse with minimal edits.
2
Faded thermal receipt
Low-confidence OCR should be highlighted and easy to correct.
3
Rotated / angled receipt
Still attempt parsing; provide rotate or retake recovery.
4
Non-receipt image
Show a clear failure state and offer manual expense entry.
5
No printed total
Compute total from parsed items and ask user to confirm.
6
₹100 split 3 ways
Must reconcile exactly: ₹33.34 + ₹33.33 + ₹33.33.
7
Camera denied
Fallback to file upload.
8
Offline after first visit
Saved data should remain; OCR can work if assets/models are cached.
9
Many expenses, mixed payers
Settlement recommendations should reduce transactions correctly.

The build is divided so all five members can work in parallel without waiting for deployment. Official PS points 1–22 are owned inside the five build roles. Point 23 (Live deployment) is intentionally kept outside the parallel split and is done only after the integrated build is stable.

Member 1 • UI/UX + Frontend Experience

Role: Product Flow, Interaction Design & Responsive Frontend

Owns how the product feels on mobile and desktop, especially the scan → review → assign → settle journey.

Official PS points owned

  1. Review and correction
    • Every parsed field must be editable; users can add or delete lines.
    • Words with low OCR confidence must be visually highlighted.
    • Show the original image beside the parsed table for easy comparison.
  1. Itemized assignment
    • Assign each line item to one or more members, e.g., via drag-and-drop or tap-to-toggle avatars.
    • A shared item is split among its assignees; an unassigned item must be flagged before saving.
  1. Accessibility
    • Keyboard navigation, screen-reader labels and sufficient colour contrast.

Delivers to integration: polished reusable UI components and screens wired against shared interfaces/mock data.

Member 2 • OCR + Receipt Parsing

Role: Image Processing, OCR & Receipt Understanding Pipeline

Owns everything from receipt image input to structured, editable bill data.

Official PS points owned

  1. Receipt capture
    • Upload a receipt image (JPG/PNG) or capture one using the device camera.
    • Show an image preview before processing.
    • Run OCR with a visible progress indicator; the interface must stay responsive.
  2. Line-item parsing
    • Convert raw OCR text into a structured table of item name, quantity, unit price and line total.
    • Detect subtotal, tax lines (including CGST/SGST), service charge, discount and grand total where present.
    • Ignore noise such as addresses, GSTIN numbers, phone numbers and footer text.
  1. Total validation
    • Warn the user when the parsed items, taxes and charges do not add up to the detected total, showing the difference.
  1. Auto-categorization
    • Categorize each item into Food, Groceries, Travel, Utilities, Entertainment, Other.
    • Users can override any category; the model must load lazily so it never blocks the first screen.
  1. Multi-receipt batch scan
    • Process several receipts in one go, e.g., all bills from a trip.

Delivers to integration: stable OCR/parser functions + worker messages + structured receipt output contract.

Member 3 • Expense + Split Engine

Role: Core Expense Logic, Split Modes & Financial Correctness

Owns all per-expense calculations and rules that determine each member's exact share.

Official PS points owned

  1. Manual expenses
    • Add an expense without a receipt: description, amount, payer, participants and date.
  1. Flexible split modes
    • Support four modes per expense: equal, exact amounts, percentages and shares (e.g., 2:1:1).
    • Validate inputs: percentages must total 100% and exact amounts must total the bill.
  2. Proportional tax, charges and discounts
    • Distribute tax, service charge and discounts in proportion to each member's item subtotal, not equally.
  3. Rounding reconciliation
    • Individual shares must add up exactly to the bill total, to the paisa.
    • Any rounding remainder must be assigned by a documented rule.
  1. Recurring expenses
    • Monthly items such as a Wi-Fi recharge that are added automatically each cycle.

Delivers to integration: pure calculation functions + validation + unit tests, independent of React.

Member 4 • Balances + Settlement

Role: Group Balances, Debt Simplification & Settlement Utilities

Owns who owes, who is owed, and how the group settles efficiently after combining all expenses.

Official PS points owned

  1. Balances view
    • Show each member's net balance in the group (owes or is owed), updated after every expense.
  1. Debt simplification
    • Compute the minimum number of transactions needed to settle all balances across every expense in a group.
    • Let users mark a suggested payment as settled.
  1. UPI settle-up
    • Generate upi://pay deep links and QR codes for each suggested payment, pre-filled with payee, amount and note.
  2. Spending analytics
    • Charts of spending by category, by member and over time.
  1. Export
    • Download a settlement summary as PDF or CSV.

Delivers to integration: group balance engine + settlement recommendations + analytics/export utilities.

Member 5 • State + Persistence + Integration

Role: Data Model, Local Storage, Shared Contracts & App Integration

Owns the data foundation and glue that allows all other parallel modules to work together safely.

Official PS points owned

  1. Groups and members
    • Create, rename and delete groups.
    • Add and remove members with a name and an optional avatar or colour.
    • Switch between multiple groups from a single dashboard.
  1. Persistence
    • All groups, expenses and settlements survive a page refresh using localStorage or IndexedDB.
  1. Sharing without a backend
    • Export and import a group as JSON, or encode its state into a shareable URL.
  2. PWA and offline mode
    • Installable on phones and usable offline once the models are cached.

Delivers to integration: shared TypeScript types, state APIs, IndexedDB layer, import/export plumbing and integrated app state.

Final Shared Task • After Build Integration

23. Live deployment

Hosted on Netlify, Vercel or GitHub Pages with a public URL.

When: only after all five parallel workstreams are merged, smoke-tested and the core judging flow works end-to-end.
Owner: any one team member can perform it, with another member verifying the production build on phone and desktop.
Important: deployment is not treated as Member 5's parallel responsibility and should not block feature development.

8. Useful Team FAQ

Do we need a backend?

No for the core app. The browser runs the logic locally. A backend is only optional for extra features such as cloud sync.

Where does the parsing logic run?

Inside the browser as TypeScript/JavaScript. OCR/ML can run in Web Workers; the parser and financial logic run as local modules.

What if OCR is wrong?

That is acceptable if the correction flow is smooth. The app should highlight uncertain words and allow quick editing.

What should we test first?

Real receipt OCR on day one, plus split/rounding/settlement unit tests as early as possible.

What is the biggest integration risk?

Different members inventing incompatible data structures. Shared interfaces and ownership boundaries matter more than framework choice.
